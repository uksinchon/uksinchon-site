**현 단계 권장 범위:** D01~D04의 호환 보강과 대표 글 검증을 먼저 한다. 새 CMS 설치, `/articles/` 이사, 모든 과거 글 일괄 재작성, 전면 SSG 전환, 미디어 전체 이전은 첫 구현에 포함하지 않는다.

## 2. 매일 콘텐츠 작업과 개발을 병행하는 방법

기존 CMS가 운영 계정에서 사용 가능한지는 R00에서 확인한다. 사용 가능하면 직원은 현재 도구로 초안을 계속 작성하고 관리자가 기존 절차로 검토한다. 새 필드가 준비될 때까지는 원고 안에 ‘적용 조건·공식 링크·확인일·검토 요청 사항’을 메모할 수 있다. 이번 조사에서 계정을 만들거나 실제 원고를 저장하지는 않았다.

직원에게 매번 SEO 항목을 직접 채우게 하지 않는다. 직원이 해야 할 일은 실제 질문, 확인한 사실과 출처, 신촌점의 판단, 사진 사용 범위다. 개발자는 주소·메타·시각 처리·링크·미리보기와 공개본 분리를 책임진다. 새 홈페이지가 완성될 때까지 일상 콘텐츠 작성을 미루지 않는다.

큰 흐름은 **정보·운영 확인 → 고정 구조와 데이터 의미 확정 → 편집·표시 보강 → 대표 5개 검증 → 제한 공개·관찰 → 주제와 홈 확장 → 과거 글 선별 확대**다. 검색 성과를 기다리는 동안에도 초안과 공식 자료 검토는 계속할 수 있다.

| **R11** | 저장소·캐시·SSG 재평가. R00 수치와 R06 이후 사용량 확보 후 | 실제 이미지 총량/증가율·D1 사용량·TTFB·비용·공개 내림 요구를 근거로 유지/확장을 결정. R2라면 ID별 바이트 해시·접근 권한·구형 URL·캐시 무효화·복구 검증. SSG라면 발행 지연·미리보기·개별 복구까지 비교 | 별도 설계와 승인 범위. R2 복사 완료 전 기존 BLOB 삭제 금지. 프레임워크 전환을 앞 단계의 완료 조건으로 만들지 않음 |

R00의 미확인이 남아 있어도 R01~R05의 로컬 설계·검증은 진행할 수 있다. R06의 실제 공개 검증은 읽을 수 없는 운영 상태를 성공으로 대체하지 않는다. 원래 사이트 접근이 정상인 경우 불필요한 정책 변경은 하지 않는다.

## 3. 콘텐츠 모델과 날짜 처리 계약

### 고정 식별자·버전·공개본

- 기존 `cms_posts.id`, `slug`, `published_revision` 구조를 유지한다. 제목과 카테고리는 주소 생성의 입력으로 다시 사용하지 않는다.
- snapshot에 `schemaVersion`을 도입한다. 없는 기존 값은 v1로 읽고, v2는 확장 메타를 받는다. 원고 전체를 곧바로 변환하지 않는다.
- 작성 중 버전과 공개 승인된 버전을 계속 분리한다. 공개 메타·관련 글·이미지·날짜도 공개 승인본에서 읽는다.
- `contentType`은 `guide`, `comparison`, `case`, `news` 등을 실제 운영에 맞춰 지원한다. FAQ는 독립 필수 유형이 아니라 필요한 본문 구성이다. 모든 글에 같은 ‘정답→표→FAQ’ 순서를 강제하지 않는다.
- 카테고리는 안정적인 코드와 표시 라벨을 분리한다. 관련 글은 UUID 배열로 보관하고 공개 시 현재 canonical 경로로 해석한다. 비공개/삭제 글 링크는 공개본에서 제외하거나 검토 경고한다.

### 필드 제안과 입력 책임

| 정보 | 직원/검토자가 입력·판단 | 시스템 처리 |
|---|---|---|
| 제목·본문·유형·카테고리 | 작성자는 실제 질문과 안내, 유형 선택. 요약 초안은 선택 가능 | 글 ID·고정 주소·버전, 제목/요약 기반 기본 메타. 자동 요약도 공개 전 검토 가능하게 표시 |

편집 화면 기본 입력은 제목·본문·카테고리·유형 중심으로 두고, 글에 해당하는 검토 항목만 연다. 입학·비용·비자·약사 자격처럼 조건이 중요한 글은 공식 근거와 적용 시점이 미확인인 상태로 확정 안내를 발행하지 못하게 한다. 문체 교정·사진 교체만으로 사실 확인까지 완료 처리하지 않는다.

### 세 날짜와 운영 시각

1. **`publishedAt`**: 자사 사이트에서 최초 공개 승인된 시각. 기존 `published_at` 의미 유지. 네이버의 `sourcePublishedAt`는 원문 이력으로 별도 보관하며 자사 발행일을 소급 덮어쓰지 않는다.
2. **`contentModifiedAt`**: 독자의 판단에 영향을 주는 실제 내용·조건·주요 설명이 바뀐 버전을 공개한 시각. 단순 저장·검토 요청·재승인·제목 오탈자만 고친 경우 자동 갱신하지 않는다. 변경 사유와 검토자의 판단을 기록한다.
3. **`factCheckedAt`**: 특정 revision의 특정 자료·주장을 실제 재확인한 날짜. 내용이 그대로여도 확인 행위가 있었다면 별도 기록할 수 있다. 그러한 행위 없이 오늘 날짜를 자동 입력하지 않는다.
4. `draftUpdatedAt`, `approvedAt`, `sourceFetchedAt`, `sourcePublishedAt`는 운영·출처 이력이다. 위 세 날짜의 대체값으로 공개하지 않는다.

최초 공개 시 이후의 실질 수정이 없으면 `dateModified`는 최초 공개 시각과 같게 하거나 명확한 정책에 따라 생략한다. 최초 공개 전 초안 저장 시각을 ‘공개 글 수정일’로 출력하지 않는다. 이후 승인본의 `contentModifiedAt`을 가시 수정일·JSON-LD·sitemap lastmod에 일관되게 사용한다. 사실 확인만 했다면 확인일만 표시하고 lastmod를 신선도 신호로 조작하지 않는다. RSS pubDate는 최초 발행일을 유지한다.

기존 글의 정확한 실질 수정일을 모르면 버전 저장 날짜를 검토 완료 날짜로 변환하지 않는다. 이벤트·승인 이력을 대조하고, 복원 불가능한 필드는 미확인 또는 생략으로 처리한다.

예시 검증 시나리오(가상 일정): 첫 공개 → 다음 날 오탈자 교정 → 자료 재확인만 수행 → 입학 조건을 실질 수정. 각 단계에서 공개일은 고정, 작업 시각은 변화, 사실 확인일은 실제 확인 단계에만 변화, 수정일·lastmod는 실질 수정 공개 때만 변화해야 한다.

## 4. 본문·표·이미지 확장 범위

기존 Delta를 유지하면서 이미지 속성과 **검증된 표 블록**을 추가하는 안을 우선 비교 구현한다. 임의 HTML을 저장해 표를 표시하는 방식은 사용하지 않는다. `cleanSnapshot`, `renderDelta`, `imageIds`, 편집기, 원고 내보내기/불러오기, 버전 복원, 네이버 초안 저장이 새 블록을 함께 이해해야 한다. 현재 `imageIds`가 객체 insert를 사진으로 간주하는 부분도 같이 다뤄야 한다.

표는 열·행 수와 텍스트 길이를 제한하고 헤더·단위·출처를 보존한다. 모바일에서는 표 영역을 가로로 읽을 수 있게 하되 페이지 전체가 옆으로 밀리지 않게 한다. 중요한 결론은 표 밖에서도 읽을 수 있게 쓴다. 표를 이미지로 대체하는 것을 완료 조건으로 삼지 않는다.

이미지 alt는 자산 전체보다 **글에서 사용한 맥락**에 붙인다. 같은 사진이 다른 글에서 쓰일 때 설명이 달라질 수 있기 때문이다. 파일 자체의 폭·높이·크기·해시·저장 위치는 미디어 메타로 분리한다. 첫 화면 주요 이미지는 lazy 일괄 적용을 풀지 측정하고, 아래쪽 사진은 lazy를 유지한다. OG·대표 이미지가 없을 때 실제 브랜드 이미지를 쓸지 생략할지도 명시하며 임의 학교 이미지나 권리 불명 사진을 만들지 않는다.

## 5. 상세·목록·내부 링크의 완료 기준

### 개별 글

- JS를 끄거나 초기 HTML만 받아도 승인된 h1·요약·본문·표·이미지 설명·출처·담당자·날짜·다음 글 링크를 읽을 수 있어야 한다.
- canonical은 응답마다 하나이며 최종 공개 URL과 일치한다. 추적 쿼리·제목 변경으로 새 canonical이 생기지 않는다.
- `BlogPosting`/`Article`은 실제 유형에 맞추고 headline·작성자·날짜·대표 이미지가 화면과 일치해야 한다. 실제 인물/조직 정보만 사용한다. 작성자 고유 소개와 BreadcrumbList는 본문·경로가 있을 때 적용한다.
- FAQPage·llms.txt 추가 여부는 위 기준의 통과 조건이 아니다. 문의 버튼 클릭을 `Lead` 또는 실제 상담 접수로 자동 간주하지 않는다.
- 비공개 초안·저장 실패·검수 누락·동시 수정·공개 내림에서 승인본과 미디어 공개 범위가 정확히 유지되어야 한다.

### 페이지네이션·카테고리

- 공개 글 25개 이상인 가상 데이터로 12/12/1개 페이지와 이전·다음 링크를 확인한다. JS 버튼 클릭 없이 고유 URL로 접근 가능해야 한다.
- `/blog/`, `?page=2`, `?page=3`은 각각 자기 canonical. 2페이지를 1페이지로 합치지 않는다.
- `?page=1`·잘못된 숫자·페이지 범위 밖·임의 category·복수 필터·추적 쿼리의 기대 응답을 표로 정해 검증한다. 존재하지 않는 깊은 페이지는 유효 콘텐츠인 것처럼 200을 주지 않는 안을 권장한다.
- 현재 카테고리 필터는 검색 제외 목적을 분명히 하고, canonical을 실제 필터 경로와 맞출지 별도 주제 안내로 이행할지 결정한다. 필터 페이지에서 글 발견이 가능하도록 `nofollow` 일괄 적용은 재검토한다. robots로 막아 noindex를 읽지 못하게 만드는 조합은 피한다.
- 주제 안내가 준비되면 `/topics/{stable-code}/`와 그 2페이지도 고유 URL·초기 HTML 링크·자기 canonical을 가진다. 같은 글은 어디서 들어와도 동일 상세 URL이다.
- 발행 시각 동률 정렬의 보조 키를 추가하고 새 글 삽입 상황을 확인한다. 더 큰 규모의 커서 방식 전환은 데이터가 필요성을 보일 때 결정한다.

## 6. 대표 5개 검증 계획

선정 원문·본문 확보 근거는 [진단서 7절](seo-audit.md#7-대표-글-표본-5개)에 있다. 아직 자사 글이 만들어지거나 발행됐다는 뜻은 아니다. 자사 글 ID/주소는 실제 초안 생성 후 비공개 검증표에 기록한다.

**확대 게이트:** 5개 표본의 기술 검증과 담당자 검토가 완료되고 실제 사용 중의 수정 비용·누락을 검토한 뒤 R10을 시작한다. Google 대표 URL이나 현장 데이터가 아직 생기지 않았다면 ‘데이터 대기’로 남기고 제한 공개 범위를 유지하며 원인을 확인한다. 확인되지 않은 검색/AI 성과를 근거로 대량 자동 발행으로 확대하지 않는다.

## 주소 대응과 리디렉션 계획

기존 주소를 유지하는 것이 기본이다. 다음은 **제안 대응표**이며 실제 리디렉션을 설정하지 않았다. 실제 기존 글 ID·별칭·외부 링크 목록은 운영 접근 후 R00에서 확보한다.

| 현재/가능한 변형 | 제안되는 대표 URL·처리 | 조건 |
|---|---|---|
| `/` | `/` 유지 | 초기 홈 디자인만 단계적으로 확장 |
| `/blog/story-{UUID}/` | 동일 주소 유지, 제목/분류 변경과 무관 | 전체 `/articles/` 이전 안 함 |
| `/pharmacy/`, `/seminar-2027/` | 동일 주소 유지 | 종료 행사 상태·본문 개선은 주소 변경과 분리 |
| `/study-path/`, `/hello-uk/` | 주소·상담 도구 역할 유지, 검색 정책은 명시적 검토 | 모든 도구를 글처럼 색인시키지 않음 |
| `/index.html`, 정적 경로의 `index.html`, 슬래시 변형 | 실제 호스팅 정규화 확인 후 필요한 경우만 대표 경로로 301/308 | 기존 Cloudflare 처리와 중복/순환 방지. 로컬 압축 파일 더블클릭 경로를 깨지 않는 웹 전용 처리 |
| `https://www.uksinchon.com/{path}` | 필요하면 `https://uksinchon.com/{path}`로 301/308 | 현재 응답 미확인. 경로와 필요한 광고 쿼리 보존, 도메인 설정 변경은 별도 범위 |
| `/blog/?page=2` | 같은 2페이지 유지·자기 canonical | 모든 page를 루트로 리디렉션하지 않음 |
| 기존 `?category={한글라벨}` | 최초에는 기존 필터 유지. 주제 안내 도입 시 일대일 대응 확인 후 해당 `/topics/{code}/` 검토 | 페이지 번호 의미·필터 결과가 같은지 확인. 모든 필터를 같은 허브로 무차별 이동하지 않음 |
| 향후 명시적으로 바꾸는 글 주소 | 검증된 일대일 구주소→최종 새주소 영구 리디렉션 | 대상 글 UUID·제목·구/신 URL·이유·승인·검증 결과 기록. 내부 링크·canonical·sitemap·RSS 함께 교체 |

주소 변경이 필요할 때는 먼저 비공개 대응표를 확정한다. 새 URL이 같은 내용의 200인지, 접근 권한이 맞는지 확인하고 리디렉션을 한 번에 연결한다. 임의로 모든 404를 홈으로 보내지 않는다. 추적 쿼리는 canonical에서 제외하되 유입 측정에 필요한 값을 무조건 삭제하지 않는다. 개별 비공개/삭제 글은 적절한 404/410 정책을 쓰며 무관한 새 글로 보내지 않는다.

리디렉션 유지 기간은 외부 링크·검색 수집을 고려해 장기로 잡고, 최소 1년을 운영 기준으로 검토한다. 구주소의 검색 반영은 즉시 되돌아오지 않으므로 주소 이동을 일반 UI 변경보다 비싼 결정으로 취급한다.

## 데이터 백업·변환·검증·복구 계획

### 적용 조건

현재 권장안은 추가 필드와 호환 읽기를 우선하므로 즉시 전체 데이터를 변환할 필요가 없다. 실제 기존 데이터 수정·미디어 이동·새 형식 쓰기를 시작하는 후속 작업에서는 다음을 수행한다. **이번 단계에서 백업·내보내기·변환·복구를 실행하지 않았다.**

1. **범위 고정:** 변경할 표/필드/본문 버전/미디어와 대상 ID를 선정한다. 운영 D1·미디어·별칭·이벤트를 포함한 기준선을 기록한다. 실제 요금제의 백업·복구 기능과 보존 기간은 계정/최신 공식 문서로 확인한다.
2. **백업:** 인증된 운영 환경에서 D1 내보내기 또는 확인된 복구 지점을 만들고, 별도 저장소라면 객체/메타도 같은 기준 시점으로 보관한다. 암호 해시·비공개 초안이 포함될 수 있어 공개 Git·정적 사이트 폴더에 두지 않는다. 백업 성공 로그와 해시·복구 방법·책임자를 남긴다.
3. **복구 연습:** 보호된 별도 환경에서 먼저 복원해 글·버전·공개 포인터·미디어 수, slug 유일성, 관계, 본문/파일 해시를 대조한다. 백업 파일 존재만으로 복구 가능 판정하지 않는다.
4. **호환 추가:** 기존 형식을 읽는 코드부터 배포할 계획을 세운다. 새 필드는 unknown/null을 허용해 근거 없는 검토일·담당자를 만들지 않는다. schemaVersion과 변환 버전을 기록한다.
5. **소규모 변환:** 대표 5개 또는 가상 복사본에서 dry run을 수행한다. 원본 스냅샷을 덮어쓰지 않고 새 버전/추가 메타로 반영한다. 동일 작업 재실행으로 중복 글·미디어가 생기지 않아야 한다.
6. **검증:** 변환 전후 대상 수·ID·URL·slug·공개 승인본·날짜 의미·본문 텍스트·이미지 해시/권한·내부 링크·sitemap을 대조한다. 미확인 값이 ‘검토 완료’로 바뀌거나 구형 내보내기/복원이 새 필드를 지우지 않는지 확인한다.
7. **운영 적용:** 일괄 작업 중 직원 쓰기와 충돌하지 않도록 짧은 쓰기 제한 또는 버전 조건부 갱신·변경 추적을 사용한다. 변경 후 새 글/승인 이력을 보관한다. 보호된 리허설을 통과한 묶음만 적용한다.
8. **복구:** 잘못된 공개 글은 이전 승인본을 재승인하거나 앞으로 수정하는 방식으로 좁게 복구한다. 스키마는 추가 필드를 남긴 채 호환 코드로 돌아갈 수 있어야 한다. 전체 DB 복원은 최후 수단이며 기준 시점 이후의 새 글·수정·계정 변경을 별도로 보존·재적용하지 않은 채 덮어쓰지 않는다.

R2 이동을 선택하면 **복사 → ID별 해시·권한 대조 → 일부 읽기 전환 → 전체 읽기 전환 → 관찰 → 나중에 원본 정리** 순서다. 기존 `/media/{id}`를 유지하고 저장 위치만 바꾸면 Delta 전체를 변환할 필요가 없다. 초안/내려간 글의 사진이 공개 버킷이나 긴 CDN 캐시에 남지 않도록 설계한다. 권한 확인·캐시 무효화 비용을 측정하기 전 영구 공개 캐시를 넣지 않는다.

## 7. AI 접근·측정 운영 절차

### 서비스별 정책 확정

R08은 [진단서 8절](seo-audit.md#8-공식-지원-여부와-ai-서비스별-접근-정책)의 서비스별 표를 출발점으로 한다. 검색용 Googlebot·OAI-SearchBot·PerplexityBot 접근과 사용자 요청 조회, GPTBot 등 학습 관련 수집을 별도 열로 관리한다. Google-Extended는 Gemini grounding까지 영향을 줄 수 있어 학습 차단만을 원할 때의 손익을 따로 기록한다.

현재 수집 가능성을 확인한 다음, 검색/답변의 링크 유입을 위한 접근을 우선 검토하는 안을 권장한다. 학습 허용·제한은 검색 허용의 필수 부속 항목으로 정하지 않는다. Claude·현행 Bing 정책은 공식 본문을 확보하기 전 미확인으로 유지한다. Google의 2027 예정 공유 제어를 이미 지원되는 공통 스위치로 구현하지 않는다.

실제 적용에서는 robots 내용뿐 아니라 최종 HTML·X-Robots-Tag·스니펫 제한·GSC 포함/상속·Cloudflare 보안 이벤트를 대조한다. 봇 요청의 시각·URL·검증 근거·최종 HTTP 상태·차단 규칙을 기록하고, UA 문자열만으로 허용하거나 보안 전체를 끄지 않는다. 설정 변경은 이전 값과 범위를 저장하고 적용 후 같은 방식으로 재검증한다.

| Google 생성형 AI | Settings → Search generative AI 실제 포함/상속 확인. 별도 성과 보고서의 노출수·페이지·날짜/PT·기기/국가 확인 | 월별 및 설정 변경 후. 보고서 부재는 권한/데이터/제외를 구분. Web 보고서와 중복 합산 안 함 |
| 다른 AI | 서비스·질문·언어·조회일·지역/로그인 맥락·인용된 URL을 가진 소규모 고정 질의군. 링크 유입과 인용을 구분 | 월별. 답변 변동·개인화·표본 한계를 기록, 모든 모델의 인용률로 일반화하지 않음 |
| 상담 | 버튼 클릭, 실제 수신 문의, 유효 상담, 지원 진행을 각각 집계. 카카오톡 앱 전환/붙여넣기/수신 누락과 referrer 누락을 구분 | 직원 주간 집계 + 월별 검토. 개인정보를 URL·이벤트로 보내지 않음. 클릭을 접수 완료로 세지 않음 |

이번 조사에서는 성능 수치를 측정하거나 추적 코드를 추가하지 않았다. 새 측정 도구·이벤트·외부 수집은 후속 범위에서 별도 검토한다. 현재 블로그 CSP의 `script-src 'none'`와 새 RUM/분석 필요성도 함께 판단해야 하며, 기존 픽셀을 무조건 모든 글에 복사하는 방식은 계획에 포함하지 않는다.

## 8. 커밋·검증 결과·복구 연결

커밋은 ‘SEO 전체 개선’ 하나로 묶지 않는다. 다음은 후속 구현의 예시이며 실제 커밋을 만들지 않았다.

| 논리 단위 | 연결 번호 | 검증 기록 |
|---|---|---|
| `seo(R01): preserve publication URL contracts` | R01 | 구/신 URL 기대 응답표·제목 수정 후 URL 불변·리디렉션 루프 없음 |
| `cms(R02): read versioned editorial metadata` | R02 | v1 읽기, unknown 필드, 기존 공개본 동일성·백업 리허설 |
| `cms(R02): record publication and factual review dates` | R02 | 저장/오탈자/재검토/실질 수정의 세 날짜·lastmod 일치 |
| `editor(R03): add contextual image metadata` | R03 | 원고 재조회·권리·alt·width/height·비공개 사진 |
| `editor(R03): support validated comparison tables` | R03 | 표 편집·안전 렌더링·모바일·구형 복원·imageIds 호환 |
| `seo(R04): align public metadata and pagination` | R04 | HTML/JSON-LD/공개본 대조·25개 경계·빈 페이지·카테고리 정책 |
| `home(R07): expose published stories and curated topics` | R07 | 초기 HTML 링크·실제 공개 글·빈 주제/종료 추천 제외 |
| 서비스별 접근·설정 변경 | R08 | 공식 근거·이전/새 설정·실제 검증된 요청·복구 값. Git 밖 설정이면 별도 변경 기록 |
| 수집/AI/Cron 각각의 활성화 | R09 | 실제 수집/초안·실행·비용·실패·검수 무효화. 공개 승인과 분리 |

각 PR/커밋 설명에는 **로드맵 번호, 문제와 달라진 동작, 데이터/URL 영향, 검증 명령·환경·결과, 미확인 사항, 되돌리는 방법**을 기록한다. 코드 커밋·Cloudflare 배포 ID·콘텐츠 승인 revision을 구분한다. R05~R06의 실제 원고 검수와 학생 자료는 공개 Git에 넣지 않는다.

새 필드 쓰기가 시작된 뒤 옛 코드를 되돌리면 데이터를 버릴 수 있으므로 ‘git revert 가능’만으로 가역성을 주장하지 않는다. 스키마 추가·호환 읽기·새 쓰기·렌더링을 분리하고, 되돌릴 때도 새 데이터를 읽을 수 있는 버전을 유지한다.

## 9. 후속 구현 범위 검토안

**첫 구현 묶음으로 권장:** R00 운영 기준선 확인, R01 고정 URL 계약, R02 날짜/출처/검토의 호환 모델, R03 이미지/표·직원 입력, R04 상세/목록의 SEO 기본, R05 대표 5개 검증, R06 제한 공개 확인. R08 중 읽기 조사와 서비스별 정책 결정도 함께 하되 실제 설정은 확인된 필요에 맞춰 분리한다.

그 결과를 본 다음 R07 홈·주제 안내, R09 정기 수집·AI 활성화, R10 기존 글 확대를 이어간다. R11 저장소·렌더링 교체는 수치가 필요성을 보일 때 별도 범위로 검토한다. 네이버 공식 자료·권리 검토가 밀려도 직원의 새 초안 작성과 다음 글의 자료 정리는 계속한다.

검토가 필요한 결정은 **첫 구현 범위**, **실제 검토 담당자**, **AI 서비스의 검색/학습 정책**, **운영 계정에서 확인 가능한 근거**다. 이번 문서는 미확인 사항을 남긴 상태로 진단·비교·의존관계·복구·완료 기준까지 완성했으며 실제 구현은 후속 요청에서 시작한다.
