# 직원이 본인 글을 직접 발행하는 운영 방식

적용 기준: **2026-11-18 한국시간** · 관련 로드맵: **R02(권한·이력), R03(직원 화면), R06(검증·공개)**

후속 사용자 지시로 **공개 전 사실 확인 메뉴·세 체크 항목·기록 버튼과 일반 글 발행 시 해당 기록의 필수 조건을 제거**했다. 아래 직원 사용 순서는 이 정책을 반영한다. 초기 배포의 99개 검증 기록과 별개로 [후속 변경·검증](FACT_CHECK_PANEL_REMOVAL.md)을 기록한다.

사용자가 직원 작성 글을 본인의 검토 요청 없이 바로 게시할 수 있도록 변경하도록 지시했다. 이에 따라 직원 `author` 역할에 **본인 글의 발행·재발행·공개 내리기와 사실 확인 기록**을 허용한다. 별도의 관리자 승인이나 검토 요청 상태를 필수로 거치지 않는다.

## 직원 사용 순서

1. [직원 글쓰기](https://uksinchon.com/admin/)에 로그인하고 **새 글 쓰기**에서 원고를 작성한다. 이미 열린 창은 새로고침해 새 발행 버튼을 불러온다.
2. 저장·미리보기로 내용을 확인한다. 입학·학비·장학금 등 사실 확인이 필요한 안내에는 적용 대상, 공식 출처, 실제 자료 확인일과 대조 범위를 적는다. 별도 체크 항목이나 사실 확인 기록 버튼은 없다. 지사장에게 검토를 요청하는 절차는 필요하지 않다.
3. **발행하기**를 누르고 공개 확인 창에서 확인한다. 실제 서버 응답이 성공해야 **공개했습니다**와 **현재 공개본 보기**가 표시된다. 공개본에서 본문·사진을 확인한다.
4. 이후 수정은 초안으로 저장된다. **수정 내용 발행하기**를 누르면 같은 URL에 새 버전이 공개된다. 수정본도 별도 체크리스트 기록 없이 발행할 수 있다.
5. **공개 내리기**로 본인 글과 해당 공개 이미지의 접근을 회수할 수 있다. 원고·사진·수정 이력은 보관되며 다시 발행할 수 있다. 휴지통 삭제·복구는 관리자 업무다.

**검토 요청하기**는 선택 기능으로 남긴다. 요청 후에도 작성자가 직접 발행할 수 있다. 초안 저장이나 배포 자체로 대기 원고를 자동 공개하지 않는다. 기존 직원 계정도 같은 기능을 사용할 수 있으며 계정 재생성·관리자 승격·운영 DB 변경은 필요하지 않다.

## 조사와 대안 판단

기준 코드는 원격 `main`의 `2186430`이다. 그 커밋의 ‘신촌 UK 노트’ 명칭과 이전 편집기·표·사진·상담 기능을 먼저 반영한 뒤 변경했다. 기존 미추적 `docs/content-strategy/`는 작업·커밋 대상에서 제외했다.

확인한 파일:

- `cms/server/api.js`: `ownPost`가 관리자 또는 해당 글의 실제 작성자만 허용하고 있었다. 이후 `factcheck`, `publish`, `unpublish`에서 별도의 관리자 검사가 직원을 다시 차단했다.
- `admin/editor.js`, `admin/editorial.js`, `admin/index.html`: 직원에게 발행·공개 내리기·사실 확인 버튼을 숨기고 검토 요청을 주 동작으로 제시했다.
- `cms/server/publication.js`, `cms/server/content.js`: 공개 전 형식·출처·현재 버전 확인과 불변 공개본·날짜 분리 구조를 확인했다.
- `cms/server/naver.js`, `cms/server/naver-api.js`, `cms/server/trash.js`, `cms/server/schema.js`: 네이버 원문 대조·소유권·휴지통·역할 스키마와 독립 권한을 확인했다.
- 기존 CMS·SEO·원문 검토·휴지통 테스트, `admin/help.html`, `admin/naver-help.html`, `docs/STAFF_BLOG.md`: 기존 운영 안내와 회귀 검증 범위를 확인했다.

직원을 전부 관리자로 승격하는 안은 다른 직원 원고·계정·상담신청·네이버 수집·삭제 권한까지 확대한다. 별도 승인 설정·역할 테이블을 추가하는 안은 이번 요구에 불필요한 상태와 운영 비용을 만든다. 기존 **소유권 검사 뒤 발행 작업만 허용**하는 최소 수정안을 선택했다. URL·slug·데이터 모델·렌더링·이미지 저장 방식은 변경하지 않는다.

## 권한과 이력

| 작업 | 직원 | 관리자 |
|---|---|---|
| 본인 글 작성·저장·미리보기 | 허용 | 허용 |
| 본인 글 발행·재발행·공개 내리기 | 허용 | 허용 |
| 다른 직원의 비공개 원고와 관리 동작 | 차단 | 허용 |
| 직원 계정·상담신청·네이버 가져오기 운영 | 차단 | 기존 권한 유지 |
| 글 삭제·휴지통·복구 | 차단 | 기존 권한 유지 |

`ownPost`, 로그인·계정 활성 상태·임시 비밀번호 변경·Origin·현재 revision 검사는 유지한다. 일반 소식은 검토 요청 이벤트 없이 초안에서 발행할 수 있다. 안내의 공식 출처·적용 대상·날짜 입력 검증은 유지하되 별도 체크리스트 기록은 발행에 필수가 아니다. 기존 기록이 실제 존재할 때만 해당 검토자를 표시하며, 발행만으로 검토 기록을 만들지 않는다.

발행은 기존의 새 불변 승인 버전으로 저장된다. `publication.approvedById/Name`에는 실제 발행한 직원이 기록된다. 내부 필드 이름을 바꾸기 위한 데이터 변환은 하지 않는다. 초안은 기존 공개본과 분리되며 최초 발행일·실질 수정일·자료 확인일의 의미도 유지한다. 반복 발행은 멱등 처리하고 기존 URL은 유지한다.

네이버 원문/해시 대조와 Codex 검토 증명의 유효기간·실제 원문 재조회는 기존대로다. 관리자 소유로 가져온 글이 자동으로 직원 소유가 되거나, 직원에게 네이버 가져오기 관리 권한이 부여되지는 않는다. 사용자 요청은 직원 본인이 올리는 글의 직접 발행이다.

## 완료 기준과 검증

- 직원 세션만으로 검토 요청 이벤트·관리자 작업 없이 공개 HTML·목록·사진·사이트맵·RSS에 본인 글이 표시된다.
- 조건 안내도 별도 체크리스트 없이 발행할 수 있다. 적용 대상·공식 자료 등 유지한 입력 규칙과 실제 과거 검토 기록의 처리는 검증한다.
- 다른 직원/관리자 소유 글, 익명·다른 Origin·이전 revision·비활성 계정은 거부한다. 계정·상담·가져오기·휴지통 권한은 확대하지 않는다.
- 작성자가 직접 수정본 재발행·공개 내리기·재발행을 수행하고 원고 이력·URL·최초 발행일을 보존한다.
- 실제 Chromium에서 버튼·성공/오류 안내·사진·자료 확인·공개 페이지를 확인한다. 320/390/768/1440px에서 편집기와 글이 넘치지 않는다.

검증 데이터는 모두 로컬의 가상 계정·원고·자료·사진이다. 테스트 서버는 loopback에만 열며 운영 사이트에 테스트 글을 발행하지 않는다. 테스트 결과·배포 상태는 후속 검증 기록에 구분한다. 검색 색인·순위·AI 인용·상담 전환은 이번 권한 변경의 기술 완료 기준과 별개의 운영 성과다.

```bash
node tests/check_staff_publishing.mjs
CMS_STAFF_PUBLISH_UI_FIXTURE=1 node tests/check_staff_publishing.mjs
# 위 가상 서버를 유지한 상태에서 다른 터미널:
```

## 배포와 되돌리기

서버 권한·API 검증은 **`80ad614` (R02)**, 화면·사용 안내·화면 검증은 **`dcb9b13` (R03/R06)**, 이 운영 문서·검증 기록은 별도 문서 커밋으로 나눈다. 최종 커밋의 Cloudflare Pages 배포 체크와 실제 운영 응답은 따로 확인한다. 이 환경의 운영 접근이 거부되거나 CMS 세션이 없으면 실제 운영자 계정으로 발행까지 검증했다고 보고하지 않는다.

DB 마이그레이션·과거 원고 덮어쓰기·직원 역할 변경·대기 원고 일괄 공개는 없다. 따라서 이번 배포에는 데이터 백업·변환·리디렉션이 필요하지 않다. 코드 복구 시에는 서버·화면 커밋을 함께 되돌려 관리자 발행 방식으로 복원한다. 이미 직원이 정상 발행한 글은 코드 복구만으로 자동 비공개가 되지 않으므로, 필요한 글만 관리자가 개별 공개 내리기 한다. 발행 이력을 지우거나 DB 전체를 복원하지 않는다.
